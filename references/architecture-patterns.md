# 6种主流 Agent 架构模式

## 1. 单体 Agent (Single Agent)

**结构:** 一个 Agent + 多个 Tools，Agent 自行决定何时调用哪个 Tool。

**适用场景:**
- 任务步骤 ≤ 3，无分支
- 单一领域（如"只做数据分析"）
- 实时性要求高（秒级响应）
- 成本敏感（最少 API 调用）
- 流程可预测，不需要动态路由

**优势:** 简单、快速、token消耗低、易调试
**劣势:** 复杂任务容易丢失上下文，角色混乱，无法并行

**示例:** 
- 客服机器人（知识库 + FAQ Tool）
- 数据查询助手（SQL Tool + Chart Tool）
- 个人日程管理（Calendar Tool + Reminder Tool）

**设计要点:**
- Tool 数量控制在 5-10 个，过多会混乱
- 用清晰的 Tool description 帮助 Agent 选择
- 系统提示词限定角色边界

## 2. 流水线式 (Pipeline / Sequential)

**结构:** 多个 Agent 按固定顺序串联，前一个的输出是后一个的输入。

**适用场景:**
- 固定流程，步骤顺序不变（如：收集→清洗→分析→报告）
- 顺序依赖强（step B 必须等 step A 完成）
- 错误容忍中等（可在关键节点设检查点）
- 每步专长不同（收集Agent ≠ 分析Agent）
- 不需要动态分支

**优势:** 确定性高、易追踪、每步可独立测试、token可控
**劣势:** 不可并行、无法动态调整顺序、某步卡住全链停

**示例:**
- 研究流程：搜索Agent → 摘要Agent → 报告Agent
- 数据管线：采集Agent → 清洗Agent → 建模Agent → 可视化Agent
- 内容生产：选题Agent → 写稿Agent → 编辑Agent → 发布Agent

**设计要点:**
- 每个Agent的系统提示词明确输入格式和输出格式
- 关键节点设人工审批门（human-in-the-middle）
- 输出格式标准化（JSON schema），减少下游解析错误

## 3. 编排/指挥官式 (Orchestrator / Dispatcher)

**结构:** 一个指挥官Agent接收指令，判断任务类型，分发给专业子Agent，汇总结果。

**适用场景:**
- 动态路由（不同任务走不同子Agent）
- 多领域专长（每个子Agent擅长不同领域）
- 需协调多个子Agent的结果
- 任务类型不确定，需先判断再行动
- 中等实时性（多一次路由判断，增加1-2秒延迟）

**优势:** 灵活路由、子Agent独立优化、可扩展（加新子Agent不影响已有）
**劣势:** 指挥官判断错误会走错路、多一层token开销、调试链路更长

**示例:**
- 数据助手指挥官：→ 学习Agent / 分析Agent / 视觉Agent
- 客服编排：→ 退款Agent / 技术Agent / 销售Agent
- DevOps编排：→ 监控Agent / 部署Agent / 安全Agent

**设计要点:**
- 指挥官的系统提示词必须有清晰的路由规则（不是"自由判断"）
- 子Agent之间通过共享目录或消息传递结果，不直接对话
- 指挥官做最终汇总和质量把关
- 设置fallback：路由失败时走默认Agent

## 4. 层级式 (Hierarchical)

**结构:** 多层指挥结构，上级分配任务、审批结果，下级执行并上报。

**适用场景:**
- 错误容忍极低（每步需审批）
- 有管理层角色（如：战略Agent → 执行Agent）
- 需要权限控制（某些操作只有上级能批准）
- 任务可分解为管理层+执行层
- 需要质量把关和风险控制

**优势:** 严格质量控制、权限分层清晰、风险可控
**劣势:** 速度慢（每步审批）、token开销大、容易官僚化

**示例:**
- 金融交易：风控Agent审批 → 交易Agent执行 → 合规Agent复核
- 医疗诊断：初诊Agent → 专家Agent审批 → 处方Agent执行
- 法律审查：检索Agent → 分析Agent → 合规Agent审批 → 执行Agent

**设计要点:**
- 明确审批条件（不是"所有都审批"，而是"超过阈值才审批"）
- 上级Agent的审批规则写在系统提示词中
- 设置超时机制：上级15秒未审批，按预设策略自动处理
- 审批日志留痕，便于追溯

## 5. 黑板式 (Blackboard / Shared Memory)

**结构:** 多个Agent围绕一个共享"黑板"读写，各自独立工作，通过黑板感知全局状态。

**适用场景:**
- 子任务强耦合，需实时感知彼此进展
- 共享上下文量大（如：所有Agent需要同一份长文档）
- 动态协作（Agent A的发现影响Agent B的策略）
- 并行但有交叉依赖
- 需要渐进式推理（多轮迭代，每轮更新黑板）

**优势:** 共享上下文自然、Agent自主协作、无需中心调度
**劣势:** 黑板状态管理复杂、并发冲突需解决、调试困难

**示例:**
- 代码审查：安全Agent / 性能Agent / 风格Agent 共读同一段代码，各自写评论到黑板
- 竞品分析：价格Agent / 功能Agent / 市场Agent 各自调研，共享发现互相补充
- 故障诊断：日志Agent / 指标Agent / 链路Agent 各自分析，黑板汇总推理

**设计要点:**
- 黑板数据结构要清晰（分区：事实区、推理区、结论区）
- 设置读写规则（谁写哪个区、谁读哪个区）
- 加版本号或时间戳防止冲突
- 设置终止条件（黑板达到某个状态时停止迭代）

## 6. 去中心化/Mesh (Decentralized)

**结构:** Agent之间直接对话协商，无中心节点，平等协作。

**适用场景:**
- 子任务完全独立，无需协调
- 可试错（某个Agent失败不影响全局）
- 追求灵活性和鲁棒性
- 没有天然的管理者角色
- 容忍结果不确定性

**优势:** 最灵活、单点故障不影响全局、自然扩展
**劣势:** 协调成本高、结果不确定、容易死循环或冗余对话、调试极难

**示例:**
- 多人辩论：正方Agent vs 反方Agent vs 评委Agent，自由讨论
- 众包标注：多个Agent独立标注同一数据，投票决定
- 探索式研究：多个Agent各自探索不同方向，定期交流发现

**设计要点:**
- 设置最大轮次防止死循环
- 定义对话协议（请求/响应/广播格式）
- 加入收敛机制（投票、权重、仲裁Agent）
- 监控token消耗，设置总预算上限
